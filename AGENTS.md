# x_connector

Проект двусторонней связи между ноутбуком (Windows) и сервером (Linux) по **аудиоканалу** — через звуковые разъёмы, без сетевых интерфейсов, USB и радиоканалов.

Документ служит контекстом для ИИ-агента. Раздел «Оригинальный текст задания» — исходная формулировка владельца проекта, менять её нельзя. Раздел «Структурированная сводка» — техническая расшифровка того же задания. При расхождении приоритет у оригинального текста.

## 2. Структурированная сводка

### 2.1 Цель

Управлять сервером с ноутбука силами ИИ-агента, работая по аудиоканалу. Сервер не должен требовать подключения к сети, USB-периферии или монитора с клавиатурой для своего управления.

### 2.2 Физическая схема канала

Два независимых однонаправленных аудиопровода, вместе — дуплекс:

| № | Разъём на ноутбуке (Windows) | Разъём на сервере (Linux) | Направление |
|---|---|---|---|
| 1 | аудиовыход (наушники) | аудиовход (line-in) | ноутбук → сервер |
| 2 | микрофонный вход | аудиовыход | сервер → ноутбук |

Название проекта («x_connector», «икс коннектор») происходит от перекрещенной схемы двух проводов. Практическая реализация этой схемы при разных типах разъёмов — в разделе 3.4.

Оба направления работают одновременно, поэтому нужна либо разнесённая по частям работа, либо честный полный дуплекс с развязкой наводки и эха.

### 2.3 Способ модуляции

Ориентир автора — передача данных звуком «как с аудиокассет на компьютеры с Z80 в 80–90-х» и «как по факсу». Практически это означает FSK/AFSK-класс модуляции с опорой на существующие реализации, а не разработку модулятора с нуля:

- классика кассетных форматов — EAR/TAPE, импульсно-частотная разметка байтов стартовый бит / 8 бит / стоповый бит;
- классика факсимильной передачи — V.29/V.17, а также пакетный радиоканал AFSK 1200 бод и Bell 202;
- готовые инструменты: `minimodem` (GNU/Linux, FSK/AFSK/PSK/OFDM из командной строки), `Dire Wolf` (софт TNC, AX.25, сборка под Windows возможна).

Итоговый формат модуляции, скорость и помехоустойчивость выбираются на этапе прототипа по замерам на реальном железе, с учётом того, что у ноутбука и сервера разные звуковые кодеки, АРУ и шумоподавление, которые надо отключить.

### 2.4 Состав программного обеспечения

Две взаимодействующие части, обменивающиеся только звуком:

1. **Клиент — на ноутбуке, Windows.** Управляет сеансом, кодирует исходящие символы в звук, декодирует входящий звук, показывает экран терминала сервера, готовит установочную флешку.
2. **Агент — на сервере, Ubuntu или другая Linux-система.** Декодирует входящий звук, исполняет полученные действия на сервере, кодирует в звук обратный поток.

Обе части общаются исключительно декодируя и кодируя аудиосигнал. Никаких сетевых соединений между ними по условию задания нет.

### 2.5 Сценарий первоначальной установки

Первоначальная загрузка агентной части на сервер выполняется переносом через съёмный носитель, потому что на момент установки канал связи ещё не работает:

1. На ноутбуке запускается клиент, вставляется флешка.
2. В клиенте нажимается кнопка — он записывает на флешку агентную часть (принимающую и отправляющую аудиосигнал) и всё необходимое для её установки.
3. Флешка переносится на сервер и монтируется.
4. С флешки на сервер устанавливается агентная часть.
5. Ноутбук и сервер соединяются двумя аудиокабелями по схеме из 2.2.
6. На ноутбуке запускается соединение.

Требование к содержимому флешки: установка на сервере не должна требовать интернета, сборки из исходников и отсутствующих пакетов. Только носитель и кабели.

### 2.6 Два варианта развития прямого направления

Автор предлагает два и просит предложить своё. Оба предполагают, что по звуку летят символы, а не пакеты сетевого протокола.

**Вариант A — классический SSH поверх аудиоканала.** Аудиоканал используется как последовательный порт-переходник, поверх него поднимается SSH (например, `ssh -o ProxyCommand=...` поверх виртуального COM/PTY-канала). Даёт шифрование, аутентификацию, сессии, пересылку портов и SFTP. Цена: большой объём трафика для узкого аудиоканала, необходимость удержания установочного рукопожатия при высоком битрейте ошибок, задержки на переключении направления.

**Вариант B — эмуляция клавиатуры.** Ноутбук передаёт символы так, как если бы к серверу была подключена физическая клавиатура, сервер их принимает как ввод. Минимальный объём данных, нет сетевой стековой обвязки, поведение предсказуемо на слабом канале. Цена: нет шифрования, нужна сторона на сервере, которая легально принимает такой ввод (например, вход в консоль, `getty`, `tty`-петля или HID-эмуляция через отдельный USB-кабель, если он допустим), и нет передачи файлов.

**Рекомендация.** Начать с B как с базового канала, который заведомо работает на низкой скорости и в шуме, и поверх него строить доставку файлов и команд по подтверждённым блокам. A рассматривать как надстройку на канале, когда измеренная частота ошибок станет достаточно низкой. Если HID-эмуляция недопустима (только звук), то B реализуется как приёмник на стороне сервера, публикующий ввод в `tty` через `uinput`, а не как реальная клавиатура.

### 2.7 Обязательное требование обратного направления

Назад, на ноутбук, возвращается **видеокартинка терминала сервера в виде символов**. Не поток `stdout` построчно и не снимок экрана растром, а именно текстовое состояние терминала — сетка символов, которую видит оператор сервера в консоли.

Следствия, которые нужно учесть в проекте:

- на сервере нужен эмулятор терминала, снимающий посимвольную сетку (строк × столбцов) с атрибутами курсора, а не просто перехват вывода команд;
- нужен протокол перерисовки: целиком при сбросе экрана и частями при обычных изменениях, иначе узкий аудиоканал не пропустит полную переотправку кадра;
- нужен ответ на запросы терминала (размер окна, режимы), чтобы работающие на сервере программы (`vim`, `top`, `htop`, инсталляторы) отображались корректно;
- целевая совместимость — VT100/ANSI как разумный минимум.

## 3. Решения владельца проекта

Зафиксировано 19.09.2026 после обсуждения открытых вопросов раздела «Открытые вопросы».

### 3.1 USB-кабель допустим

Условие «только звук» не является абсолютным: USB-кабель между ноутбуком и сервером разрешён.

Что при этом остаётся звуковым: управляющий поток «ноутбук → сервер» и обратный поток «экран терминала → ноутбук». USB не заменяет аудиоканал в рабочем режиме, он закрывает три задачи, которые звуком не решаются или решаются плохо:

| Назначение USB | Зачем | Без USB |
|---|---|---|
| Первичная установка агентной части | Сценарий с флешкой из раздела 2.5 — это и есть USB | Не решается: агент нельзя доставить по каналу, который ещё не работает |
| Эмуляция клавиатуры на уровне HID | Микроконтроллер (ATmega32U4, RP2040, ESP32-S3) определяется сервером как обычная USB-клавиатура | Программная инъекция в `tty` требует уже установленного агента и прав root — курица и яйцо |
| Отладочная консоль | Аварийный канал при деградации аудиосвязи, вывод логов агента | Придётся разбирать схему и перетыкать кабели |

Возможность HID-реализации прямого направления (вторая строка таблицы) ценна тем, что работает **до** установки какого-либо ПО на сервере — на входе в `getty`, на экране входа, в консоли восстановления. На первой установке она не требуется, см. 3.3; она закрывает будущую фазу «слепого подъёма канала».

### 3.2 Назначение канала — консоль починки сети, а не замена сети навсегда

Ключевой мотив проекта. Сеть на сервере есть и нужна, но напрямую соединить ноутбук и сервер проводной или беспроводной сетью не получается: проблемы с сокетами, VPN, топологией сети. X-connector подключается к серверу как отдельный, внеполосный канал, через который ИИ настраивает сервер так, чтобы его сеть заработала нормально.

Отсюда четыре следствия, которые важнее выбора модуляции:

1. **Канал обязан не использовать сетевой стек.** Он работает именно потому, что это звуковая карта, а не сетевой интерфейс: никакие сокеты, маршрутизация, VPN и брандмауэр его не касаются. Прямой запрет: не рассматривать подъём IP поверх звука (PPP/SLIP/эмуляция модема) как базовый вариант. Он вернул бы зависимость от того самого сетевого стека, который в данный момент и диагностируется, и сделал бы канал непригодным ровно в тот момент, когда он нужен.
2. **Рабочий цикл — интерактивный, а не потоковый.** Типичная операция: набрать команду → дождаться → прочитать экран. Критичны задержка одного обмена и корректность читаемого вывода, а не пропускная способность. Целевая скорость канала — «команда в секунду», а не «мегабиты».
3. **Канал должен переживать худшее состояние сервера:** сломанная маршрутизация, поднятый VPN с дефолтным маршрутом, пустой DNS, включённый `nftables`, недоступный интернет, высокая загрузка CPU, отсутствие GUI. Агент не имеет права обращаться в сеть ни при каких условиях, включая установку зависимостей.
4. **После починки сети канал не выбрасывается** — он остаётся аварийной внеполосной консолью на случай повторного поломания. Отсюда требование к нему: минимальное число подвижных частей, восстановление перетыканием кабеля без переустановки, отсутствие долгого установочного рукопожатия.

Практический набор задач канала, под который он и проектируется: `ip a`, `ip r`, `ip neigh`, `ss -tunap`, `resolvectl status`, `journalctl -b`, `nft list ruleset`, правка конфигов сети (`netplan`/`systemd-networkd`/`NetworkManager`), правка конфигурации VPN, перезапуск служб, чтение длинного вывода с прокруткой, передача небольших файлов (конфиг, скрипт, ключ) в обе стороны. Потоковое видео, большие архивы и интерактивные GUI-приложения в задачи не входят.

Вариант A (SSH поверх аудиоканала) при таком назначении проигрывает дополнительно: он требует рабочего сетевого стека на сервере для `sshd` и рукопожатия, то есть перестаёт работать как раз тогда, когда сеть сломана, — а это единственный случай, когда канал нужен.

### 3.3 Первая установка — с клавиатурой и монитором на сервере

На момент первой установки к серверу подключены клавиатура и монитор. «Слепой подъём канала» — будущая фаза, не требование первого релиза.

Следствия:

- HID-микроконтроллер **не входит** в спецификацию первой сборки. Прямое направление реализуется программно на уже установленном агенте.
- Первичная установка выполняется человеком физически: сервер с монитором и клавиатурой, загрузка/запуск установщика с USB-флешки, запуск агента, после чего монитор и клавиатура убираются, дальнейшая работа идёт по звуку.
- Установка обязана быть полностью автономной: все зависимости лежат на флешке, обращений в интернет нет (см. следствие 3 пункта 3.2). На целевой машине нет ни компилятора, ни, вероятно, рабочего репозитория.
- Приёмка первой сборки проверяется так: оператор один раз запускает установщик с клавиатуры, затем работает с сервером только через X-connector, не прикасаясь к нему руками.

### 3.4 Физическая реализация — любая, X-схема или Y-разветвители

Схема из двух проводов (2.2) реализуется практически, тип разъёма — не ограничение. Правило выбора:

| Ноутбук | Сервер | Коммутация |
|---|---|---|
| Разнесённые разъёмы | Разнесённые | X-схема двумя проводами, без разветвителей |
| Комбинированный (TRRS) | Разнесённые | Y-разветвитель со стороны ноутбука |
| Разнесённые | Комбинированный (TRRS) | Y-разветвитель со стороны сервера |
| Комбинированный | Комбинированный | Y-разветвители с обеих сторон |

Технические последствия, обязательные к учёту при выборе модуляции и уровне звука:

- **Стандарты TRRS.** CTIA и OMTP меняют местами контакт микрофона и землю. Неподходящий Y-разветвитель — «микрофон не видит сигнал». Нужен CTIA (современный ноутбук) либо переходник OMTP.
- **Питание электретного микрофона.** На контакт микрофона комбинированного разъёма подаётся смещение порядка 1,5–2,5 В через резистор 1–10 кОм. В тракт передачи данных нужен разделительный конденсатор (0,1–1 мкФ), иначе смещение попадёт в тракт источника.
- **Различие уровней.** Выход для наушников — порядка 0,3–1,5 В, полное отклонение mic-входа — 10–50 мВ. В сторону mic-входа нужен делитель (типично последовательно 1 кОм, шунтирующий 100–220 Ом, подбирается замером), иначе клиппинг и несъёмный сигнал.
- **АРУ и шумоподавление убивают FSK.** В Windows отключаются «улучшения обработки микрофона», автоматическая регулировка усиления, подавление шума и эха. На Linux — `module-echo-cancel`, автоусиление и вообще весь слой PipeWire/PulseAudio: захват вести напрямую из ALSA (`hw:`), уровни выставлять через `amixer`, а не ползунком микшера.
- **Перекрёстные наводки в Y-разветвителе.** В одном 4-полюсном штекере и в одном общем кабельном жгуте оба направления идут параллельно и делят землю — наводка ближнего конца неизбежна. Поэтому Y-разветвитель хуже X-схемы, и там, где он есть, нужен либо частотный разнос направлений, либо честный полудуплекс с ожиданием подтверждения.
- **Контур заземления.** Две машины, запитанные от разных розеток, дают фон 50 Гц по общему проводу. Лечится питанием одной машины от другого блока, разделительными трансформаторами по каждому аудиотракту, либо питанием сервера от ноутбука по USB.

Приоритет при сборке: там, где разъёмы разнесены, ставить перемычку напрямую; Y-разветвитель применять только где комбинированный разъём не даёт другого варианта.

Длина аудиокабеля — **не более 2 метров** (решение владельца). Следствия:

- Ёмкость линии порядка 100–200 пФ, затухание в полосе до 20 кГц на такой длине ничтожно — кабель не ограничивает полосу и не диктует нижний предел скорости. Ограничителями остаются кодеки, АРУ и наводки в разветвителях.
- Наводка ближнего конца в Y-разветвителе от длины кабеля не зависит, она от соседства проводников в одном штекере — этот риск остаётся при любой длине.
- Контур заземления тоже остаётся: короткая линия его не убирает, требования к разделительным конденсаторам и питанию от одного блока в силе.

### 3.5 Базовый режим — полудуплекс с подтверждением

Принято решение: **полный дуплекс не является базовым режимом**. Обмен строится по циклу «одна сторона передаёт кадр → другая подтверждает → смена направления».

Мотивировки:

- рабочий цикл канала и так полудуплексный — «набрать команду → дождаться → прочитать экран» (см. 3.2, следствие 2);
- в приёмнике в каждый момент времени только одно направление, поэтому наводка ближнего конца из Y-разветвителей и эхо из комбинированных разъёмов перестают быть проблемой — не нужно адаптивное эхоподавление;
- резко сокращается число подвижных частей, что соответствует требованию 3.2 про аварийную консоль с минимумом настройки;
- режим не зависит от типа коммутации: работает и на X-схеме, и на Y с обеих сторон, без переделки протокола.

Полный дуплекс возможен как будущая оптимизация после замеров чистоты X-схемы на конкретном железе. Протокол проектируется так, чтобы включение дуплекса не требовало смены кадрирования.

### 3.6 Шифрование содержимого канала не требуется

Принято решение владельца: шифрования нет, потому что при работе он физически находится у сервера с ноутбуком, а не удалённо. Физический доступ к кабелю того же человека, который стоит у машины, не считается угрозой.

Что это снимает: слой `libsodium`/secretbox, обмен ключами, аутентификацию канала. Канальный уровень ограничивается обнаружением ошибок (CRC) и повтором по подтверждению.

Принятые остаточные риски, зафиксированы, чтобы были известны:

- по каналу пойдут открытые тексты конфигураций сети и VPN, пароли и ключи;
- при работе через облачного ИИ-агента (см. 3.7) снимки экрана сервера передаются в облако по интернету ноутбука — это отдельный путь утечки, независимый от аудиоканала и шифрования;
- если в будущем понадобится работа с сервером без физического присутствия, это решение пересматривается: тонкий слой шифрования на `libsodium` дешевле, чем перестройка протокола, но в открытом канале его потом не добавить.

### 3.7 ИИ-агент работает на ноутбуке и в облаке, ноутбук с интернетом

Уточнение владельца: **ноутбук подключён к интернету, ИИ-агент облачный**. Полный офлайн-режим (локальная модель на ноутбуке) — отложенная фаза, не требование первой сборки.

Что это меняет:

- Клиенту на ноутбуке не нужен собственный LLM-клиент и не нужен офлайн-режим. Клиент обязан предоставлять **удобную управляемую программу**, которой ИИ-агент пользуется с ноутбука: отправить команду, получить снимок экрана, дождаться, передать файл. Роль «мозга» выполняет ИИ-агент, вызывающий клиент, а не сам клиент.
- Флешка для сервера перестаёт быть автономной по содержимому в смысле подготовки: зависимости и пакеты скачиваются на ноутбуке, где интернет есть, и переносятся. Автономность требуется в момент установки на сервере, а не при подготовке флешки.

Что остаётся в силе и отменяемо не считается: **серверная часть обязана работать полностью без сети**, включая установку и запуск зависимостей. Причина — сервер как раз в состоянии сломанной сети (см. 3.2, следствие 3). Интернет на ноутбуке к серверу не переносится: общий провод у нас звуковой, а не сетевой.

## 6. Соглашения

- Язык документации и комментариев — русский.
- Идентификаторы в коде — английский.
- Файлы проекта — UTF-8.

### 6.1 Два каталога и ветки

Один git, два рабочих дерева. Агенты **не работают в одной папке**.

| Агент | Каталог | Ветки |
|---|---|---|
| Cursor (этот чат) | `D:\projects\x_connector` | `wip/cursor-<тема>` |
| Claude | `D:\projects\x_connector-claude` | `wip/claude-<тема>` |

Второе дерево — `git worktree`. Общая история, разные checkout. Список: `git worktree list`.

Правила:

- Открывать в IDE только свой каталог. Чужой не монтировать как workspace и не делать в нём `git checkout`.
- Перед правками — ветка от актуального `master`: Cursor `wip/cursor-<тема>`, Claude `wip/claude-<тема>`. Латиница, дефисы, без даты.
- Не переключаться на чужую `wip/*`. Одна и та же ветка не может быть checkout сразу в двух деревьях.
- `master` не держать занятым «на всякий случай». Слияние в `master` — по явной просьбе владельца; сначала `git worktree list`, чтобы `master` не был checkout в другом каталоге.
- Перед стартом: `git status` в своём каталоге. Чужие незакоммиченные файлы не затирать.

Кто чем занят — в `wip/cursor.md` и `wip/claude.md` **своего** каталога. Это разные файлы на диске (разные ветки), плюс правило 6.2.

### 6.2 Файл занятости

Перед любой правкой агент читает оба файла в `wip/` и пишет только свой.

| Файл | Кто пишет |
|---|---|
| `wip/cursor.md` | только Cursor |
| `wip/claude.md` | только Claude |

Формат — короткий YAML в начале файла (его же читает человек):

```yaml
status: active   # active | idle
worktree: D:/projects/x_connector
branch: wip/cursor-<тема>
task: одно предложение
hands_off:
  - путь или маска файлов, которые сейчас трогает этот агент
updated: 2026-09-20T21:44+03:00
```

Правила:

- Свой файл можно перезаписывать целиком. Чужой — не открывать на запись.
- `status: active` — второй агент не берёт файлы из `hands_off`.
- Задача сдана или прервана — сразу `status: idle`, `hands_off: []`, ветку не удалять.
- Файл занятости коммитится вместе с задачей в **своей** ветке.
