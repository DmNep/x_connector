# Мануал x_connector

Как собрать тракт, запустить канал и понять, что сломалось. Спецификация кадров и тонов — в [protocol.md](protocol.md). Решения «зачем так» — в [AGENTS.md](../AGENTS.md).

Версия пакета: `xconn_channel` **1.0.0** (первая сборка, 2026-09-26). Это релиз, не бета: приёмка 3.3 на живом X-кабеле пройдена.

## 1. Что это за система

Две программы и два аудиопровода.

1. **Клиент** работает на ноутбуке под Windows. Это управляемая программа: отправить команду, нажать клавишу, получить текстовый экран терминала. «Мозг» (ИИ-агент) сидит на ноутбуке и ходит в интернет; сам клиент LLM не содержит.
2. **Агент** работает на сервере под Linux. Он слушает звуковую карту, пишет принятые символы в PTY (обычно `bash`), держит эмулятор VT100 и отдаёт снимки сетки обратно звуком.

Между ними нет IP, SSH, PPP и сокетов. Канал нужен как раз тогда, когда сеть сервера сломана.

Типичный рабочий цикл: набрать команду → подождать около секунды → прочитать экран. Целевая скорость — «команда в секунду», не мегабиты.

## 2. Что нужно

### Люди и машины

| Сторона | ОС | Роль |
|---|---|---|
| Ноутбук | Windows | клиент, интернет для ИИ |
| Сервер | Ubuntu или другой Linux | агент, сеть может быть полностью мёртвой |

На **первой установке** к серверу подключены клавиатура и монитор. Слепой подъём канала — отдельная будущая фаза.

### Кабели

- Два аудиопровода **не длиннее 2 м**, схема «крест» (X) либо Y-разветвители, если разъём комбинированный (TRRS).
- USB-флешка понадобится для переноса агента на сервер. Рабочий обмен по USB не идёт.

### Программы

- Python 3.10 или новее. На Windows — лаунчер `py` (`python` из Microsoft Store не использовать).
- Только стандартная библиотека. `pip install` на сервере не требуется и не должен требоваться: у сервера может не быть интернета.
- На Windows для живого звука клиент использует `winmm`, на Linux агент — ALSA устройство `hw:`, минуя PulseAudio/PipeWire.

Компилятор, ffmpeg, sox, minimodem для работы канала не нужны.

## 3. Физическое подключение

### 3.1 X-схема (предпочтительна)

Когда у обеих машин отдельные разъёмы на наушники и микрофон/line-in:

| Провод | Ноутбук | Сервер |
|---|---|---|
| 1 | аудиовыход (наушники) | аудиовход (line-in) |
| 2 | микрофонный вход | аудиовыход |

Это и есть «икс». Направления разведены по разным штекерам — меньше наводка ближнего конца.

### 3.2 Y-разветвители (если разъём TRRS)

Комбинированный 4-полюсный разъём не даёт воткнуть два отдельных провода. Тогда нужен Y-разветвитель на этой стороне. Если TRRS с обеих сторон — разветвители с обеих.

Стандарт контактов: современные ноутбуки — **CTIA**. OMTP меняет местами микрофон и землю: «микрофон молчит». Нужен CTIA либо переходник.

Y хуже X: оба направления идут в одном штекере и делят землю. Протокол из‑за этого полудуплексный: в каждый момент передаёт только одна сторона, эхо и наводка не попадают в приёмник как полезный сигнал.

### 3.3 Уровни

Выход наушников — порядка 0,3–1,5 В. Полное отклонение mic-входа — 10–50 мВ. В сторону микрофонного входа нужен **делитель** (типично последовательно 1 кОм и шунт 100–220 Ом, подбирается замером). Иначе клиппинг, и FSK не разбирается.

На контакт микрофона комбинированного разъёма подаётся смещение ~1,5–2,5 В. В тракт данных — разделительный конденсатор 0,1–1 мкФ, иначе постоянная составляющая уходит в источник.

Две машины от разных розеток дают фон 50 Гц по общей земле. Лечится питанием от одного блока, разделительными трансформаторами по тракту или питанием сервера от ноутбука по USB (USB здесь только питание, не канал).

### 3.4 Что отключить обязательно

АРУ и шумоподавление убивают FSK: чистые тона для них — «шум», и они их давят.

**Windows (ноутбук)**

- Панель звука → записывающее устройство (микрофон) → свойства.
- Снять «улучшения»: АРУ, подавление шума, подавление эха.
- Уровень подобрать так, чтобы пик был около −12 dBFS, без красной зоны клиппинга.

**Linux (сервер)**

- Захват и воспроизведение — с `hw:`, не с `default`, не через Pulse/PipeWire.
- Не грузить `module-echo-cancel` и автоусиление.
- Уровни — `amixer`, не ползунком десктопного микшера.

Проверка тракта — раздел 8.

## 4. Установка программ

Пакет на ноутбуке не ставится в site-packages: команды из корня репозитория.

```text
git clone https://github.com/DmNep/x_connector.git
cd x_connector
py -m unittest discover -s tests
```

### 4.1 Запись флешки (ноутбук)

Вставить флешку, записать агент и установщик:

```text
py -m xconn_channel stick E:\
```

Без пути команда перечислит съёмные диски Windows. На флешку попадают `xconn_channel/`, `install.sh`, unit systemd, `README.txt`, автономный Linux CPython (`python-linux/`, x86_64 и aarch64) и `alsa-debs/` (`aplay`/`arecord`/`amixer` для Ubuntu jammy/noble/resolute). На этом шаге ноутбуку нужен интернет, если кэша ещё нет. Повторная запись без сети: кэш уже лежит в `packaging/python-linux/` и `packaging/alsa-debs/`, либо `stick --no-fetch`.

### 4.2 Установка на сервер

Клавиатура и монитор ещё подключены. Интернета на сервере нет и не требуется.

```text
sudo mkdir -p /mnt/usb
sudo mount /dev/sdX1 /mnt/usb
cd /mnt/usb
sudo sh install.sh
```

Скрипт копирует пакет в `/opt/x_connector`, распаковывает встроенный python3 в `/opt/x_connector/python`, при отсутствии `aplay` ставит `alsa-utils` из `alsa-debs/$VERSION_CODENAME` (`dpkg -i`, без apt), заводит пользователя `xconn` в группе `audio`, даёт ему `NOPASSWD` sudo (`/etc/sudoers.d/xconn-agent`) и ставит `xconn-agent.service`. Повторный `install.sh` не сбрасывает уже прописанные `XCONN_CAPTURE` / `XCONN_PLAYBACK`.

Устройства:

```text
arecord -l
aplay -l
sudoedit /etc/default/xconn-agent
sudo systemctl start xconn-agent
sudo systemctl status xconn-agent
```

Потом монитор и клавиатуру можно убрать, дальше — только звук.

## 5. Первый запуск без кабеля

Loopback — оба конца в одном процессе, звуковой карты нет. Так проверяется, что Python, пакет и PTY живы.

На ноутбуке из корня репозитория:

```text
py -m xconn_channel loopback -c "echo hello"
```

Ожидается сетка терминала с выводом команды (заголовок вида `24x80 cursor=...` и текст экрана). Кодировка консоли Windows часто cp1251, псевдографика cp437 может отобразиться криво — на работу канала это не влияет.

Несколько команд подряд:

```text
py -m xconn_channel loopback -c "uname -a" -c "pwd"
```

Интерактивный режим:

```text
py -m xconn_channel loopback --repl
```

На Windows агент по кабелю не запускается: `py -m xconn_channel agent` сразу выйдет с кодом 2. Для отладки клиента без Linux используйте `loopback`.

## 6. Запуск по кабелю

Порядок:

1. Кабели воткнуты по разделу 3, АРУ выключена.
2. На сервере запущен агент.
3. На ноутбуке запущен клиент. Клиент — мастер: он шлёт `HELO` на 300 бод, агент отвечает, стороны переходят в рабочий режим 1200 бод и клиент запрашивает полный снимок экрана.

### 6.1 Сервер (агент)

Список карт:

```text
arecord -l
aplay -l
```

Прямое устройство, не `default`. Пример: карта 1, устройство 0 → `hw:1,0`.

```text
cd /opt/x_connector   # каталог, где лежит пакет xconn_channel
python3 -m xconn_channel agent --capture hw:1,0 --playback hw:1,0
```

Если вход и выход на разных устройствах — укажите их раздельно. Оболочка по умолчанию — bash в PTY. Другая:

```text
python3 -m xconn_channel agent --shell /bin/bash -l
```

Всё после `--shell` уходит в argv оболочки. Агент работает, пока его не остановить Ctrl‑C на самой машине (на первой установке монитор ещё подключён) или пока процесс не завершат иначе.

### 6.2 Ноутбук (клиент)

Список устройств и сразу понятный текст, если чего-то нет:

```text
py -m xconn_channel devices
```

Номера — winmm. `-1` — устройство по умолчанию, если список не пуст. Если микрофона или наушников нет, `client` пишет это на stderr и выходит с кодом 2, без трассировки «код 2».

```text
cd x_connector
py -m xconn_channel client --capture 0 --playback 1 --repl
py -m xconn_channel client --capture 0 --playback 1 -c "ip a" -c "ip r"
```

На этом ноутбуке карта **0** — микрофон; **1** — аналоговый выход. `--playback 0` уходит в HDMI и оставляет эфир тихим.

После `connect` печатается сетка 24×80 (снимок при необходимости едет кусками). Дальше — как в loopback: команды, `.key`, `.ping`, `.refresh`, `.resize`, `.get`.

### 6.4 Что показало железо (2026-09-22)

Сервер: Ubuntu 26.04 (`resolute`), Realtek ALC897. Ноутбук: Windows, Realtek, улучшения микрофона выключены.

- Карта **0** — HDMI монитора. Аналог — карта **1**, устройства `pcmC1D0c` / `pcmC1D0p`.
- Чистый `hw:1,0` с `-c 1` даёт `Channels count non available`. Рабочий путь: `plughw:1,0`.
- Без пакета `alsa-utils` агент падает: `No such file or directory: 'aplay'`. Пакеты лежат на флешке, не через apt.
- Несжимаемый 24×80 режется на `SCREEN_PART`. Старый агент без нарезки по-прежнему даёт `nak=0x03` — клиент тогда жмёт окно до 8×32.
- Повторный HELO: клиент пробует `probe`, затем `base`. Агент после сеанса слушает 1200 бод — без этого шага эфир молчит до restart.
- После записи флешки нужен `systemctl restart xconn-agent`, не только `start`: иначе процесс держит старый `vt100.py` в памяти.
- Ubuntu 26.04: в sudoers **не** писать `Defaults:xconn !requiretty` — visudo 1.9.17+ отвергает неизвестную настройку и откатывает весь файл.
- VT100 глотает OSC (`ESC ] … BEL`/`ST`): semantic prompt systemd больше не протекает в сетку как `3008;start=`.
- Помпа ждёт, пока в PTY есть foreground (`TIOCGPGRP`); клиент на CMD/KEY держит `T_CMD_CARRIER` и режет ввод длиннее 240 байт. Приёмка 3.3 (работа без консоли сервера) пройдена 2026-09-25.

### 6.3 Что происходит при рукопожатии

1. Клиент передаёт в режиме `probe` (300 бод, тона Bell 202 1200/2200 Гц).
2. Агент молча слушает: порог по энергии, преамбула, CRC. Мусор отбрасывает без ответа.
3. На верном `HELO` агент отвечает своим `HELO` (версия протокола, размер экрана).
4. Несовпадение версии — ошибка, не тихая деградация.
5. Клиент запрашивает полный снимок, дальше работа в `base` (1200 бод).

Перетыкание кабеля не требует переустановки: клиент снова начинает с `HELO`.

## 7. Справочник CLI

Общий вид:

```text
py -m xconn_channel [-V] {loopback|client|agent|stick|devices} [опции]
```

| Флаг | Где | Смысл |
|---|---|---|
| `-V`, `--version` | все | версия пакета |
| `-c`, `--command` | loopback, client | команда на сервер; флаг можно повторять |
| `--repl` | loopback, client | читать команды со stdin |
| `--backend` | все | `winmm`, `alsa` или `wav`; по умолчанию по ОС |
| `--capture` | client, agent | вход: номер winmm или `hw:N,M` |
| `--playback` | client, agent | выход: номер winmm или `hw:N,M` |
| `--shell …` | loopback, agent | argv оболочки агента, всё после флага |
| `--no-fetch` | stick | не скачивать Linux python3, только кэш |
| `devices` | команда | список входов/выходов; если чего-то нет — сразу текст, что подключить |

В `--repl`:

| Ввод | Действие |
|---|---|
| любая строка без точки | `CMD`: строка плюс `\n` в PTY |
| `.key имя` | клавиша из таблицы ниже |
| `.put LOCAL [NAME]` | файл на сервер в `inbox/` |
| `.get REMOTE [LOCAL]` | файл с сервера (абсолютный путь или имя в `inbox/`) |
| `.ping` | `PING` / `PONG`, экран не перерисовывается |
| `.refresh` | полный снимок экрана |
| `.resize R C` | размер сетки PTY (например `.resize 12 40`) |
| `.quit` / `.exit` | выход из REPL |

Имена клавиш: `ctrl-c`, `ctrl-d`, `ctrl-l`, `ctrl-z`, `tab`, `enter`, `esc`, `up`, `down`, `left`, `right`, `backspace`, `home`, `end`.

Программы на сервере вроде `vim`, `htop`, `less` получают размер окна через PTY (`TIOCGWINSZ`) и ответы VT100 на запросы терминала. Мышь и GUI не поддерживаются.

Передача файлов: `.put local.conf` кладёт файл в `inbox/` на сервере (кадры `FILE_*`, CRC-32 на каждый файл). Небольшой конфиг по-прежнему можно набрать в консоли.

## 8. Калибровка тракта

До работы по кабелю и после смены разъёмов:

```text
py tools/probe.py --selftest
```

`--selftest` не трогает звуковую карту: синтетический тон −12 dBFS и плоская АЧХ. Так проверяется, что сам анализатор жив.

Разбор заранее записанного моно WAV 16 бит, 16 или 48 кГц:

```text
py tools/probe.py --wav capture.wav
```

Живой прогон на этом ноутбуке:

```text
py tools/probe.py --live --capture 0 --playback 1
```

`--playback 0` уходит в HDMI. Без `--live` — `--selftest` или `--wav`.

Что смотреть в отчёте:

| Замер | Норма | Если плохо |
|---|---|---|
| Шум и порог gate | порог на 12 дБ выше RMS шума | поднять уровень или убрать фон 50 Гц |
| Пик | около −12 dBFS, без клиппинга | делитель / громкость выхода |
| АРУ | амплитуда чистого тона не плывёт | выключить улучшения микрофона и echo-cancel |
| Свип 300–3400 Гц | нет «мёртвых» участков в полосе тонов | другой вход (line-in вместо mic), другой кодек |
| 2200 Гц к 1200 Гц | завал не больше 6 дБ | сместить пару тонов вниз и зафиксировать в отчёте |

Целевой пик модулятора — амплитуда 8192 из 32768 (−12 dBFS). Клиппинг даёт гармоники во второй тон и ломает FSK.

## 9. Тесты

Из корня репозитория, без железа:

```text
py -m unittest discover -s tests
```

Количественный замер BER/FER на кабеле (не часть приёмки 1.0.0 — консоль уже принята качественно):

```text
py tools/ber.py --live --capture 0 --playback 1 --frames 32
```

Скрипт гоняет эталонные кадры через звуковые карты и пишет FER/BER для `probe` и `base`. `--selftest` без железа проверяет только DSP (там нули — норма). Режим `stretch` (2400 бод, тона 1400/3400 Гц) в 1.0.0 выключен: его нельзя включать, пока нет такого отчёта на целевом тракте и явного согласия владельца.

## 10. Как устроен обмен (кратко)

Клиент — единственный мастер. Агент сам передачу не начинает.

```
клиент  REQ ──► агент
клиент  ◄── RESP
клиент  ACK ──► агент
        (тишина GAP)
```

Кадр: преамбула 0x55 вне 8N1, sync 0x7E, тип, seq, длина, payload, CRC-16/CCITT-FALSE. Максимум payload 240 байт.

Модуляция: CPFSK, тона Bell 202.

| Режим | Бод | Тона, Гц | Зачем |
|---|---|---|---|
| `probe` | 300 | 1200 / 2200 | захват канала, HELO |
| `base` | 1200 | 1200 / 2200 | рабочий режим |
| `stretch` | 2400 | 1400 / 3400 | не входит в 1.0.0; выключен до отчёта BER `--live` |

Экран — сетка 24×80, zlib. Первый кадр и сброс — полный снимок, дальше дельты по строкам.

Шифрования нет. Полный дуплекс не базовый режим. IP и SSH поверх звука не делаются.

Подробности: [protocol.md](protocol.md).

## 11. Типичные задачи на сервере

Канал рассчитан на диагностику сети, не на замену SSH навсегда:

```text
ip a
ip r
ip neigh
ss -tunap
resolvectl status
journalctl -b
nft list ruleset
```

Правка netplan / systemd-networkd / NetworkManager, конфиг VPN, перезапуск служб, чтение длинного вывода с прокруткой. Потоковое видео, большие архивы и GUI — вне задачи.

## 12. Диагностика

| Симптом | Куда смотреть |
|---|---|
| `loopback` печатает экран, кабель — тишина | кабели перепутаны местами; CTIA/OMTP; выбран не тот `hw:` / номер winmm |
| Есть несущая, кадры с CRC NAK | клиппинг, АРУ, делитель, фон 50 Гц; прогнать probe |
| Первый кадр после паузы всегда теряется | фаза преамбулы; см. protocol.md раздел 11, пункт про поиск sync |
| Агент на Windows | так задумано; агент — Linux, на Windows только `loopback` |
| «нет устройства записи» / «нет устройства воспроизведения» | подключить гарнитуру или карту; `py -m xconn_channel devices` |
| `vim` / `htop` «зависли» | должен отвечать эмулятор VT100; если воспроизводится в loopback — это уже баг агента, не тракта |
| Псевдографика в консоли Windows кракозябрами | OEM-кодировка консоли vs cp437; на сетку в памяти не влияет |
| Канал «есть», команды исполняются дважды | не должно: повтор того же `seq` отдаёт закешированный ответ, не второй запуск |
| После перетыкания кабеля мёртвый эфир | заново запустить клиент (`HELO` с `probe`); агента переставлять не нужно |
| `aplay: No such file` / агент код 2 | нет `alsa-utils`; `sudo sh install.sh` с флешки, где есть `alsa-debs/` |
| `Channels count non available` | `hw:` не умеет моно; в `/etc/default/xconn-agent` поставьте `plughw:N,M` |
| HDMI в `hw:0,0`, аналог на другой карте | смотреть `/proc/asound/pcm`: ALC/Analog, не HDMI; типично `hw:1,0` |
| `nak=0x03` на `.refresh` / команде | старый агент без нарезки; обновить с флешки или `.resize 8 32` |
| После NAK агент не отвечает на HELO | клиент 0.4 сам повторит HELO в `base`; иначе `systemctl restart xconn-agent` |
| visudo: unknown setting `requiretty` | Ubuntu 26.04; в sudoers только `xconn ALL=(root) NOPASSWD:ALL`, без `!requiretty` |
| В сетке `3008;start=` | старый агент без глотания OSC; `systemctl restart xconn-agent` после записи флешки |
| Снимок посреди `ping` / `netplan apply` | нужен агент с помпой по `TIOCGPGRP` и клиент с `T_CMD_CARRIER` |

Логи агента в этой версии идут в stderr процесса. Отдельного syslog-юнита в репозитории нет.

## 13. Что не входит в 1.0.0

Первая сборка закрыта. Ниже — следующие фазы или сознательный отказ, не дыры релиза:

- Формальный отчёт BER/FER по этому кабелю. Команда `py tools/ber.py --live --capture 0 --playback 1` есть; `--selftest` без железа зелёный. Пока отчёта нет, нельзя судить о запасе канала в цифрах и нельзя включать `stretch`.
- Режим `stretch` 2400 бод (тона 1400/3400 Гц). На паре Bell 202 1200/2200 он физически неработоспособен; отдельная пара — риск завала 3400 Гц и АРУ.
- Открытие `/dev/snd` без `aplay`/`arecord` (есть стерео и `plughw:`).
- HID-клавиатура и слепой подъём канала.
- Шифрование, полный дуплекс, SSH/IP поверх звука — сознательный отказ.

## 14. Для ИИ-агента на ноутбуке

Клиент — инструмент, не автономный бот. Минимальный сценарий починки сети:

1. `py -m xconn_channel client --capture 0 --playback 1 --repl` либо серия `-c`.
2. Дождаться сетки после `connect`.
3. Снять картину: `ip a`, `ip r`, `ss -tunap`, `journalctl -b`.
4. Править конфиги через ту же консоль.
5. После каждого шага читать экран, а не полагаться на код возврата команды — его канал отдельно не передаёт, видна только сетка терминала.
6. `.refresh`, если дельта кажется неполной; `.key ctrl-c`, если процесс на сервере завис.

Не ходить с сервера в интернет «чтобы доустановить зависимость». Если на сервере нет нужной утилиты — это ограничение среды, канал его не обходит.
